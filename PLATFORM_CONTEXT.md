# Mary: обязательный контекст платформы для Codex

Этот файл нужно прочитать перед проектированием или реализацией любой страницы
Mary. Он объясняет не отдельный экран, а продуктовую систему, связи данных и
ожидаемое поведение.

## 1. Что такое Mary

Mary — единая операционная платформа для небольшого бизнеса. Она объединяет
обращения клиентов, CRM, задачи, календарь, команду, знания, интеграции,
автоматизации и аналитику.

Целевой пользователь не обязан знать термины CRM, workflow, API, AI-агент или
бизнес-процесс. Он описывает желаемый результат обычными словами, Mary собирает
нужный контекст, предлагает понятный план, показывает последствия и выполняет
действие после подтверждения, если оно необходимо.

Главная продуктовая цепочка:

`контекст бизнеса → обращение → клиент → безопасное действие → задача →
повторяемый процесс → автоматизация → результат → аналитика → улучшение`.

Mary не является дополнительным чат-ботом внутри CRM. Это основной способ
настройки и изменения системы. Операционные страницы нужны для обзора,
проверки, выбора сущности и безопасных прямых действий.

## 2. Основной принцип интерфейса

Пользователь видит бизнес-понятия, а не техническую конфигурацию.

- Настройка автоматизации происходит через диалог с Mary, а не через property
  forms, JSON, API-поля или сложный rule builder.
- Сложное изменение начинается с `Спросить Mary`.
- Mary всегда знает контекст открытой страницы и выбранной сущности.
- Перед рискованным действием Mary показывает, что изменится и кого это
  затронет.
- После выполнения пользователь видит результат и может открыть изменённую
  сущность.
- Все связанные страницы используют одни и те же сущности, а не локальные
  копии данных.

## 3. Роли и первый вход

### Базовые роли

| Роль | Основная потребность | Типичный доступ |
| --- | --- | --- |
| Владелец | Настроить бизнес и видеть результат | Все разделы, правила, команда, подтверждение чувствительных действий |
| Администратор | Поддерживать работу платформы | Интеграции, доступы, настройки, диагностика |
| Руководитель | Организовать работу команды | Входящие, клиенты, задачи, календарь, аналитика, распределение |
| Менеджер | Выполнять назначенную работу | Свои обращения, клиенты, задачи и события |
| Наблюдатель | Смотреть согласованные данные | Read-only разделы без изменения процессов |
| AI-агент | Выполнять ограниченную зону работы | Только разрешённые знания, действия и правила передачи человеку |

Роль задаёт стартовый набор прав. Изменение доступа происходит через Mary с
предпросмотром получаемых и теряемых возможностей. Чувствительный доступ
подтверждает владелец.

### Первый вход владельца

1. `CH-01`: Mary объясняет пользу и предлагает рассказать о бизнесе.
2. Пользователь передаёт сайт, соцсеть, файл или описание словами.
3. Mary показывает резюме и просит исправить неверное.
4. Пользователь выбирает первую полезную задачу.
5. Mary просит только необходимые канал, знания и участников.
6. Mary создаёт первую автоматизацию со статусом `Черновик`. Её цель и шаги
   основаны на выбранной задаче, а не на универсальном шаблоне.
7. Mary прогоняет черновик на безопасном примере без отправки сообщений и
   изменения production-данных.
8. Пользователь видит схему, результат теста и последствия запуска.
9. Только после явного подтверждения автоматизация получает статус `Активна`.
10. Первый реальный запуск создаёт первый результат: обработанное обращение,
    запись, ответ или связанную задачу.
11. Если пользователь откладывает запуск, черновик сохраняется, а остальную
    настройку можно завершить позже.

### Первый вход приглашённого участника

1. Пользователь принимает приглашение.
2. Видит роль, доступные разделы и ответственность понятными словами.
3. Mary кратко показывает текущую работу и ближайшие действия.
4. Пользователь попадает не на общую настройку, а в релевантную рабочую очередь.
5. Недоступные действия не скрываются без объяснения: интерфейс показывает, кто
   может подтвердить или изменить доступ.

## 4. Навигация

Основная навигация:

- `Чат`;
- `Автоматизации`;
- `CRM`;
- `База знаний`;
- `Интеграции`;
- `Команда`;
- `Настройки`.

Группа `CRM` содержит:

- `Входящие`;
- `Клиенты`;
- `Задачи`;
- `Календарь`;
- `Аналитика`.

`Чат` открывает полноэкранную Mary для продолжительного исследования и создания
решений. `Спросить Mary` доступно на каждой рабочей странице и открывает
контекстное окно поверх текущего интерфейса.

## 5. Глобальная модель слоёв

Порядок интерфейсных слоёв:

`страница → правая контекстная карточка → рабочее окно или Mary →
подтверждение → результат`.

Правила:

- основная страница остаётся на месте при открытии контекста;
- список сохраняет поиск, фильтры, сортировку, страницу и scroll position;
- карточка клиента, задачи, события, участника или показателя открывается справа;
- отдельная full-page карточка для этих сущностей не создаётся;
- рабочий диалог может открыться поверх списка и drawer;
- Mary открывается с ID и названием текущей сущности;
- закрытие слоя возвращает фокус на вызвавший элемент;
- Back закрывает верхний слой до смены раздела;
- deep link восстанавливает раздел, сущность и допустимый слой.

## 6. Единые сущности и связи

| Сущность | Связи |
| --- | --- |
| Клиент | Обращения, заказы, задачи, события, каналы, ответственный |
| Обращение | Клиент, сообщения, заказ, исполнитель, знания, задача, автоматизация |
| Заказ | Клиент, обращение, оплата, доставка, проблема |
| Задача | Клиент, обращение, срок, ответственный, событие, результат |
| Событие | Ссылается на задачу или самостоятельное бизнес-событие |
| Автоматизация | Триггер, шаги, знания, участники, версия, запуски |
| Запуск | Версия автоматизации, входные данные, шаги, результат, ошибка |
| Источник знаний | Версии, статус проверки, фрагменты и места использования |
| Сотрудник | Роль, доступ, доступность, нагрузка, связанные задачи и обращения |
| AI-агент | Область ответственности, знания, разрешения, уверенность, handoff |
| Интеграция | Каналы и внешние данные, права, состояние, диагностика |

Критические ограничения:

- задача в календаре — та же задача, а не копия;
- у обращения один текущий исполнитель: сотрудник или AI-агент;
- клиентская история объединяет все каналы;
- автоматизация и её запуски являются разными сущностями;
- изменение знания не переписывает историю старых решений;
- отключение интеграции не удаляет уже полученные данные;
- удаление связи не удаляет саму сущность без отдельного подтверждения.

Минимальные идентификаторы контекста:

`clientId`, `conversationId`, `orderId`, `taskId`, `eventId`, `automationId`,
`versionId`, `runId`, `sourceId`, `memberId`, `agentId`, `integrationId`.

## 7. Как связаны страницы

### Входящие → Клиент

Новое сообщение создаёт или обновляет обращение. Mary находит клиента и заказ,
проверяет знания и показывает контекст. Открытие клиента не уводит со
`Входящих`: карточка появляется справа.

### Обращение → Ответ или сотрудник

AI-агент продолжает только при достаточных данных, разрешённом действии и
достаточной уверенности. Иначе он передаёт сотруднику сообщение, резюме,
найденные данные, источники, черновик и причину передачи.

### Обращение или клиент → Задача

Задача создаётся через Mary и хранит исходную сущность. После выполнения
результат возвращается в обращение и историю клиента.

### Задача → Календарь

Наличие срока показывает ту же задачу в календаре. Перенос срока обновляет оба
раздела и предварительно показывает последствия для уведомлений и связанных
людей.

### Повторяющаяся работа → Автоматизация

Mary замечает повторение или получает прямой запрос. Она собирает процесс
обычными словами, показывает визуальную схему, проверяет её на безопасном
примере и только затем предлагает запуск.

### Автоматизация → Входящие, задачи и команда

Реальный запуск может классифицировать обращение, подготовить ответ, создать
задачу или передать работу сотруднику. Каждый результат связан с конкретным
запуском и версией процесса.

### Все результаты → Аналитика

Аналитика агрегирует факты, но каждый показатель раскрывается до исходных
обращений, клиентов, задач, сотрудников или запусков. Mary отделяет факт,
гипотезу и ограничение данных.

### Аналитика → Новый рабочий цикл

Проблема из аналитики превращается в задачу, изменение автоматизации, обновление
знаний, интеграции, команды или правила. После подтверждения начинается новый
измеримый цикл.

## 8. Поведение Mary

Универсальный flow:

1. Получить намерение пользователя и текущий контекст.
2. Проверить, достаточно ли данных.
3. Задать один понятный уточняющий вопрос, если данных не хватает.
4. Показать краткое понимание, план или черновик.
5. Отделить факты от предположений.
6. Показать источники и последствия.
7. Запросить подтверждение для отправки, удаления, изменения прав, внешнего
   действия или массового изменения.
8. Выполнить действие.
9. Показать результат и ссылку на связанную сущность.

Mary не должна:

- выполнять опасное действие молча;
- скрывать противоречие источников;
- придумывать недостающие факты;
- называть технические настройки обязательными для пользователя;
- создавать сущности, не связанные с исходным контекстом;
- отправлять реальные сообщения во время теста автоматизации.

## 9. Контракт каждого раздела

Перед изменением страницы нужно ответить:

1. Какая роль открывает страницу и с какой целью?
2. Из какого раздела и с какой сущностью пользователь пришёл?
3. Что остаётся сохранённым при открытии drawer, modal или Mary?
4. Какие прямые безопасные действия доступны без Mary?
5. Какие изменения должны проходить через Mary?
6. Что требует подтверждения и какие последствия показываются?
7. Какие сущности обновляются после действия?
8. Куда пользователь может перейти дальше?
9. Что происходит при loading, empty, no results, error, offline и no access?
10. Как этот экран работает на mobile и с клавиатуры?

Если ответов нет в задаче, сначала проверить соответствующий `*_USER_FLOW.md`.
Нельзя проектировать страницу как изолированный экран.

## 10. Визуальный язык

- Светлые белые и мягко-серые поверхности.
- Графитовая типографика и компактные outline-иконки.
- Тонкие разделители, умеренные скругления, минимальная тень.
- Скруглённые кнопки и поля, но без набора одинаковых декоративных карточек.
- Один спокойный основной акцент; статус не передаётся только цветом.
- Без градиентов, glassmorphism, неона, emoji-иконок и декоративных dashboard
  widgets.
- Chat и контекст Mary визуально центральны, но не закрывают рабочую сущность.
- Workflow — широкий белый canvas с портами, тонкими связями и компактными
  узлами: trigger — графитовый, AI/Mary — синий, сотрудник — оранжевый,
  условие — нейтральное.
